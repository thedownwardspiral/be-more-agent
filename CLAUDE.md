# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

Be More Agent is a single-file Python application (`agent.py`) that turns a Raspberry Pi into a conversational AI agent. It uses wake word detection, local speech-to-text (NVIDIA Parakeet via sherpa-onnx, with whisper.cpp as a fallback) and Silero voice activity detection, the Anthropic API (Claude) for LLM intelligence, and local text-to-speech (Piper TTS). An internet connection is required for the Anthropic API.

## Running the Project

```bash
# First-time setup (installs uv + system deps, .venv with piper-tts + anthropic SDK +
# sherpa-onnx, downloads a Piper voice into piper/, the Parakeet STT and Silero VAD
# models into models/, and builds whisper.cpp as the fallback STT engine)
chmod +x setup.sh
./setup.sh

# Configure your Anthropic API key
cp example.env .env && chmod 600 .env
# Edit .env and add your ANTHROPIC_API_KEY

# Run the agent (auto-targets DSI display via DISPLAY=:0)
uv run agent.py
```

There are no tests. Lint with `uvx ruff check agent.py` (config in `pyproject.toml`: line length 120, rules E4/E7/E9/F, E402 ignored for `agent.py`; the remaining findings are E701 one-liners) and syntax-check with `python3 -m py_compile agent.py`.

## Architecture

Everything lives in `agent.py` — a single ~2,200-line script with one main class:

**`BotGUI`** — The entire application. It's a tkinter GUI that also manages all background threads. Key sections (marked with comment banners in the file):

1. **Configuration & Constants** (top of file) — Before the GUI/audio imports, the preamble sets `DISPLAY`, computes `BASE_DIR = Path(__file__).resolve().parent` and `os.chdir`s there (so every relative path works from any launch directory), and sets up logging. That ordering is deliberate and is why ruff's E402 is ignored for `agent.py`. Then: `.env` is loaded from `BASE_DIR`; `load_config()` merges `config.json` over `DEFAULT_CONFIG` via `validate_config()` (see Configuration); `LLM_KWARGS` holds the optional `temperature` / `output_config={"effort": ...}` parameters shared by the chat stream and the warm-up call; `restrict_private_files()` chmods `.env`, `memory.json`, `agent.log` and its `LOG_BACKUP_COUNT` backups (`agent.log.1`–`.3`) to 0600 (called from `__main__`). Also defines the `BotStates` enum, the system prompt, the `TOOLS` schemas (and `TOOLS_WITHOUT_CAMERA`), `normalize_words()` (lowercase, hyphens/dashes to spaces, strip punctuation) with `CAMERA_TRIGGER_RE`, `MEMORY_WIPE_RE` and the (pre-normalized) `FILLER_UTTERANCES` / `WHISPER_ONLY_HALLUCINATIONS` sets matched against its output, `normalize_for_tts()` (spells out `$` with an optional magnitude word, "$5 million" -> "5 million dollars", reads a dash between digits as " to ", turns other en/em dashes into ", ", spells out `%`, `°C/°F/°`, `&`, `+`, `=`, digit`/`digit, `#`digit, keeps apostrophes, then strips emoji/non-speech characters), the whisper transcript regexes, and `resolve_input_device()` / `choose_input_samplerate()`, which pick a microphone (via the `input_device` config key) and a verified sample rate. The Anthropic client is created lazily by `get_llm_client()` (first called from `warm_up_logic()`) with `timeout=60.0, max_retries=1`, so a dead network stalls a turn for about 2 minutes at most; a missing `ANTHROPIC_API_KEY` raises `MissingAPIKeyError`, which the warm-up shows on the ERROR face. An empty `ANTHROPIC_API_KEY=` counts as missing.

2. **GUI Class** — Fullscreen tkinter app (800x480, designed for the Pi's DSI touchscreen). The script sets `DISPLAY=:0` via `os.environ.setdefault` before importing tkinter, so it renders to the DSI display even when launched via SSH or systemd. Loads PNG animation sequences from `faces/[state]/` directories. Face state changes based on bot state (idle, listening, thinking, speaking, error, capturing, warmup).

   **UI queue:** worker threads never touch Tk. They call `self._ui(fn, *args)`, which puts a callable on `self.ui_queue`; `_process_ui_queue()` drains it on the Tk thread (FIFO), rescheduling itself after 30 ms when the pass did work and 100 ms when the queue was empty. `set_state()` and `append_to_text()` (also used for each streamed reply chunk) go through it. `set_state()` updates `self.current_state` synchronously on the calling thread (the worker reads it right after) and queues only the drawing. The only direct `master.after` calls are `update_animation()` and `_process_ui_queue()` rescheduling themselves on the Tk thread, plus the extra `quit` queued by the signal handler (which Python runs on the main thread). The open `BOT: ` line is tracked by `_bot_line_open` (main-loop thread only) and closed by `_end_bot_line()`.

3. **Tool Execution** (`execute_tool`) — Runs tools requested by Claude via native tool use. Three tools: `get_time`, `search_web` (DuckDuckGo), `capture_image` (Pi camera via `rpicam-still`). `capture_image` returns the photo as a base64 image block inside the `tool_result`, so Claude sees it with the full conversation history. The camera tool is offered only on turns whose user text matches `CAMERA_TRIGGER_RE` (built from `camera_trigger_words`); the tool list is chosen once per turn, and a call to a tool not offered that turn gets an `is_error` `tool_result`. Any exception from `execute_tool` is also returned to Claude as an `is_error` `tool_result` instead of aborting the turn (`execute_tool` returns `(content, is_error)`, so search and camera failures it catches itself are flagged `is_error` too; an empty search result is not an error). `rpicam-still` has a 20 s timeout.

4. **Core Logic** (`safe_main_execution`) — Main loop: detect wake word or PTT → record audio → transcribe → chat → speak. Two recording modes: adaptive (wake word; ended by Silero VAD) and push-to-talk (Enter key). Both recorders return a 16 kHz float32 mono numpy array (or None for "Heard nothing."), converted from the device rate by `resample_to_stt_rate()` (`scipy.signal.resample_poly`); the ack sound plays in `_finish_recording()`. `record_voice_adaptive()` runs `_record_until_vad_end()` when `self.vad` loaded: the PortAudio callback only queues 50 ms blocks, and the main-loop thread resamples each block (`padtype="line"`) and feeds it to `sherpa_onnx.VoiceActivityDetector` (`vad_threshold`, `vad_min_silence`, `min_speech_duration` 0.25 s). When the VAD finishes a segment (speech followed by `vad_min_silence`, default 0.9 s, of quiet) it keeps listening for `vad_resume_window` (default 0.6 s; 0 stops at once): if `vad.is_speech_detected()` turns true again in that window the speaker went on after a pause, and recording continues until the next segment finishes (and another window passes). So with no resumption a recording ends min_silence + resume_window ≈ 1.5 s after the last word (the old RMS tail, but with leading silence trimmed); a pause up to ~1.2 s is bridged, 1.4 s is not (measured). It also stops after `MAX_RECORD_TIME` (30 s for the whole recording; the VAD is then flushed), or when no speech has been detected after `LEADING_SILENCE_TIME` (5 s) + `LEADING_SILENCE_GRACE` (0.5 s, covering the detector's ~0.6 s confirmation lag) and none is being detected now, which returns None. The utterance is cut from the whole recording, resampled once, from the first segment's start to the last segment's end with `VAD_PRE_ROLL` 0.3 s / `VAD_POST_ROLL` 0.2 s, since Silero puts the start a little into the first word. Without `models/silero_vad.onnx` (or sherpa-onnx) `_record_until_rms_silence()` runs instead: the old adaptive noise-floor detector with a fixed 1.5 s tail, logged once at startup. Both record paths wait 0.2 s, join the thinking-sound thread, `sd.stop()`, then wait 0.2 s more before opening the input stream (the settle that avoids the Pi 5 hardware-contention freeze; the earlier extra 0.5 s only dropped the first words, since nothing plays between the trigger and the recording). Enter toggles PTT on only while `detect_wake_word_or_ptt()` is waiting for a trigger (`awaiting_input` set, `current_state` IDLE); otherwise the press is refused, logged, and the status shows "Finishing..." for 1.5 s — so a press while a turn is still winding down (e.g. stalled after a spacebar interrupt) is never half-taken. Toggle OFF is always accepted. `handle_ptt_toggle` and the main loop share `ptt_lock`: right after a trigger the loop clears `awaiting_input`, and for a non-PTT trigger (wake word, CLI) also `recording_active`/`ptt_event`, so an Enter that landed with the wake word cannot arm PTT for the next turn. Spacebar (`handle_speaking_interrupt`) interrupts in SPEAKING, THINKING and CAPTURING; during a tool (search or camera) the loop runs no further tools, sends nothing back to Claude, and the end-of-turn cleanup deletes any photo. The wake-word listener (`_listen_loop`) uses cheap nearest-neighbor resampling, skips inference on near-silence, and retries once with fallback stream settings (blocksize 1024, high latency; still reading and resampling full 80 ms frames) before degrading to PTT.

   Speech-to-text (`transcribe_audio`) runs on the main-loop thread: the energy gate, then `_transcribe_parakeet()` when `self.recognizer` is loaded (`create_stream` / `accept_waveform(16000, samples)` / `decode_stream`, ~0.2–0.6 s on a Pi 5) or `_transcribe_whisper()` (writes `input.wav`, runs `whisper-cli`, deletes the WAV). Each logs `[STT] <engine> <seconds>`. The recognizer is loaded once in `__init__` by `_load_parakeet()` (`OfflineRecognizer.from_transducer(..., model_type="nemo_transducer", num_threads=stt_threads)`, ~3 s, ~1 GB RSS). If `stt_engine` is "parakeet" but sherpa-onnx is not importable, a model file is missing, or loading fails, it logs an ERROR naming setup.sh step 5 and the run uses whisper; `self.stt_notice` keeps that visible in the idle status ("Waiting... (Parakeet unavailable: using whisper)") for the whole run. `sherpa_onnx` is imported in a `try`, so a `.venv` without it (start_agent.sh runs `.venv/bin/python` without `uv sync`) still starts, on whisper and RMS endpointing. `_is_speech()` drops non-speech annotations and bare `FILLER_UTTERANCES` ("um", "uh", "hmm", "mm", "oh", "so", ...: a false wake on a cough) for both engines, but `WHISPER_ONLY_HALLUCINATIONS` ("you", "thank you", "okay", "bye", subtitle credits, ...) only for whisper: Parakeet does not invent "thank you" on silence, so a real one must reach Claude.

   Whisper's recordings (`input.wav`) and camera photos live in a per-run `tempfile.mkdtemp()` directory (`self.tmp_dir`), marked live by an exclusive `flock` on `tmp_dir/.lock` held for the life of the process (released after the rmtree in `safe_exit`; `tmp_lock_guard` serializes the fd between `_lock_tmp_dir` and `safe_exit`, and `_lock_tmp_dir` does nothing once exiting). The lock is taken immediately after each `mkdtemp`. `_sweep_stale_tmp_dirs()` first removes this user's `be-more-agent-*` dirs whose `.lock` is missing or not locked, so a running instance's dir is skipped. `_ensure_tmp_dir()` recreates the dir (`os.mkdir` 0700) and its lock on demand before `input.wav` or a photo is written, since systemd-tmpfiles ages out `/tmp` entries idle for 10 days; if the name now belongs to another user or is not a directory it switches to a fresh `mkdtemp` dir (callers build file paths after the call), and it raises `OSError` once `safe_exit` has started; a failed `input.wav` write is logged and treated as an empty transcription: the WAV is deleted right after whisper runs, the photo after the turn (through the UI queue, after the overlay that uses it), and the directory at exit. Audio is clipped to ±1.0 before int16 conversion. `whisper-cli` runs with a 90 s timeout and a return-code check; every segment line is joined, and `_is_speech()` drops non-speech annotations and known silence hallucinations. If the warm-up call fails, the agent shows the ERROR face ("Can't reach Claude"), plays an error sound, skips the greeting, and still starts the main loop; the message is kept in `self.startup_error`, shown in the idle status ("Waiting... (...)") and in place of "Brain Freeze!" on a failed turn, and cleared once a turn gets a response. Each loop iteration has its own `try/except`: an unexpected error logs a traceback, shows "Something went wrong" for 2 s and keeps listening; the outer handler ("Fatal Error") only covers startup. SIGTERM/SIGINT run `safe_exit()` (save memory, stop audio, remove the temp dir, quit Tk). Memory is saved after every completed turn by `save_chat_history()`: under `memory_lock`, write `memory.json.tmp` with mode 0600, fsync, then `os.replace`. It keeps the system entry plus the last 10 conversation messages; an assistant entry carries an optional `"tools"` key, the tools actually run that turn, each as `name` or `name (failed)` when it returned `is_error` or raised (first-use order, repeated labels dropped, so a failed and a later successful call of the same tool are both listed; omitted when none ran), since the `tool_use`/`tool_result` blocks themselves are not stored. `load_chat_history()` validates the file with `is_valid_memory()` (system entry first and only first, then `user`/`assistant` entries with non-empty string content and, if present, a `tools` list of strings) and starts fresh if it is malformed; files without `tools` load unchanged. With `chat_memory: false`, memory.json is never read or written, except that the memory wipe deletes a leftover one. The memory wipe fires only when the whole normalized utterance is "forget everything" or "reset (your) memory", optionally preceded by short lead-ins (ok/okay/hey/hi/um/uh/so/please/bmo/jarvis/robot, so the wake word is fine) and followed by "please" or "now"; "don't forget everything" still does nothing. The system prompt tells Claude it cannot erase its own memory and to point the user at "forget everything".

5. **Chat & Respond** (`chat_and_respond`) — Streams the response via the Anthropic Messages API with the turn's tool list and `**LLM_KWARGS`. History comes from `_history_messages()` (last `max_history_messages`, starting at a user message; an assistant entry with a `tools` trace is sent as its text plus a `\n[tools used: get_time]` line, so Claude doesn't decide an earlier answer was made up and apologize for it; the spoken and on-screen text never includes the note). The system prompt also tells Claude that a reply marked with the note came from a real tool call, so it should not apologize for it or call it made up (a "(failed)" mark means the tool ran but returned an error; it may still correct a plain factual mistake), and never to write the note itself. If Claude imitates the note anyway, `ToolNoteFilter` removes it from the stream before the screen, TTS or memory see it: text from a `[` that could still start the note (`TOOL_NOTE_START_RE`: any case, optional spaces, e.g. `[Tools used :`) is held back across deltas until `scan_tool_note()` decides. A note must close with `]` before any newline or `[` and within `TOOL_NOTE_MAX_LEN` (120) characters (`TOOL_NOTE_RE`); then it is dropped with the whitespace after it, and replaced by one space if the text before it did not end in whitespace (so "8 PM.[note]\n\nNext" becomes "8 PM. Next"). Anything else, including an unclosed `[tools used:` that hits a newline, the cap or the end of the round, is released unchanged, so a malformed note is spoken rather than real text lost (`[laughs]` and `array[3]` pass too). The output does not depend on how the text is split into deltas; a warning is logged when a note is removed. When the stream ends with `stop_reason == "tool_use"`, it executes the requested tools, appends the assistant content and `tool_result` blocks to the messages, and loops so Claude can use the results in context. At most `MAX_TOOL_ROUNDS` (5) rounds run tools; one more round is then sent with `tool_choice={"type": "none"}` (`tools=` stays, since the API rejects `tool_use`/`tool_result` blocks in messages when no tools are defined) so Claude must answer in text, and if that still yields no text the bot says "I couldn't finish that one." (also appended to the saved reply, so memory matches what was said) and logs a warning. Streamed text is buffered and flushed to TTS up to the last sentence end in the buffer (`last_sentence_end()`: `TTS_SENTENCE_END_RE` punctuation, including `…` and closing quotes, followed by whitespace; stream deltas rarely end exactly on punctuation, so the rest stays buffered) once that part meets a minimum length, preventing choppy playback of short fragments. A period after a common abbreviation, a single letter or dotted initials ("St.", "p.m.", "U.S."), or a 1-2 digit list number ("1.") is not a sentence end (`TTS_ABBREVIATION_RE`), and the end of the buffer never is ("3." may continue as "3.14"). The first chunk of a turn, and the first chunk after each tool round, only needs `TTS_FIRST_SENTENCE_MIN_LENGTH` (default 20 chars) so the bot starts talking quickly; after that, chunks need `TTS_MIN_SENTENCE_LENGTH` (default 80 chars). Text left in the buffer at the end of each round is flushed regardless of length, so short replies like "Sure!" are still spoken.

**Key threading model:** The main loop runs in a daemon thread off the tkinter main thread. TTS runs in two threads (see Piper TTS): a synth thread fed by `tts_queue` and a playback thread fed by the bounded `audio_queue`, which owns the one TTS output stream per reply and handles interrupts itself; `wait_for_tts()` returns once queued speech has been heard and that stream closed. At most one thinking-sound thread runs at a time (`_start_thinking_sound`), and it never plays while TTS is busy (`_tts_busy()`: synthesizing, speech queued in either queue, or the playback stream open); a clip is cut within 50 ms once `thinking_sound_active` clears or speech starts. The recorders join that thread (≤1 s) before their own `sd.stop()`, since stopping another thread's playback crashes PortAudio; `sd.stop()` only affects `sd.play()` streams, never the TTS `RawOutputStream`. Worker threads reach the GUI only through `self.ui_queue` (see the UI queue above). State coordination uses `threading.Event` objects; `memory_lock` serializes memory saves (main loop vs. `safe_exit` on the Tk thread).

## LLM Integration

The agent uses the **Anthropic API** (Claude) for all LLM tasks. The `anthropic` Python SDK communicates directly with Claude's Messages API — no local inference server is needed.

- **API Key**: Read from `ANTHROPIC_API_KEY` in `BASE_DIR/.env` (loaded via `python-dotenv`)
- **Model**: Defaults to `claude-haiku-5-5` (Claude Haiku 5.5). Override via `ANTHROPIC_MODEL` env var or `text_model` in `config.json`
- **Streaming**: Uses `client.messages.stream()` for real-time token delivery during conversation
- **Optional parameters**: `temperature` (default null) and `effort` (default `"low"`, sent as `output_config={"effort": ...}`) go into `LLM_KWARGS`; a null value omits the parameter. Claude 5.x models reject a non-default temperature. The chat stream's `max_tokens` is `MAX_RESPONSE_TOKENS`: 4096 when `effort` is set or `temperature` is null (the default; thinking is on by default and thinking tokens count toward the cap), else 1024. The warm-up call uses the same kwargs (`max_tokens=32`), so a mismatch fails at startup
- **Tool use**: Native Anthropic tool use (`tools=` parameter) — no prompt-engineered JSON protocol or output sniffing
- **Vision**: The `capture_image` tool returns the camera photo as a base64 image block inside the `tool_result`, so vision requests keep the full conversation history

## Speech-to-text engines (not in repo, installed by setup.sh)

`stt_engine` picks the engine; both take the same 16 kHz float32 array and share the energy gate, `_is_speech()` and the `Heard:` log.

- **Parakeet (default)** — NVIDIA Parakeet-TDT 0.6B v2, int8, run in-process by `sherpa-onnx` (pinned with `sherpa-onnx-core`, which ships its `libonnxruntime.so`; it is listed explicitly because some sherpa-onnx wheels omit it from their metadata and uv locks from them). Files: `models/parakeet-tdt-0.6b-v2-int8/{encoder,decoder,joiner}.int8.onnx` + `tokens.txt` (~650 MB), downloaded, SHA-256-checked and unpacked by setup.sh step 5. Measured on a Pi 5 with 2 threads: 0.22 / 0.56 / 0.24 / 0.43 s for 1.4 / 4.1 / 1.6 / 3.2 s clips (whisper base.en: 2.6–3.0 s), ~1 GB RSS, ~3 s load, no CPU while the user speaks. 3 threads are no faster, so `stt_threads` defaults to 2 (range 1–4). Weights are CC-BY-4.0 (attribution in README).
- **Silero VAD** — `models/silero_vad.onnx` (~0.6 MB, setup.sh step 5), run through sherpa-onnx for endpointing whatever the STT engine. With the defaults a recording ends ~1.6 s after the last word (1.1 s with `vad_resume_window` 0), the same as the RMS fallback but with mid-sentence pauses up to ~1.2 s bridged and leading silence trimmed; ~0.2–0.5 s CPU per 6.6 s recording.
- **whisper.cpp (fallback)** — Used when `stt_engine` is "whisper" or Parakeet cannot load. Speech-to-text at `./whisper.cpp/build/bin/whisper-cli`. Model and thread count configurable via `config.json` (`whisper_model`, `whisper_threads`). Defaults to `ggml-base.en.bin` with 3 threads. Benchmarked on a Pi 5: whisper pads every input to a 30s window, so transcription latency is fixed regardless of utterance length. `base.en` is the accuracy/speed sweet spot — `tiny.en` misrecognizes short questions outright, and `small.en` costs ~2x for no content gain. Threads scale 6.7s/3.5s/2.5s/2.5s at 1/2/3/4; the 4th thread buys ~40ms while starving the tkinter and audio-callback threads, so 3 is the cap.
- **Piper TTS** — Text-to-speech via the [`piper-tts`](https://github.com/OHF-Voice/piper1-gpl) Python package (installed into `.venv` from `pyproject.toml`). Voice `.onnx` + `.onnx.json` files live in `piper/`, downloaded by `python -m piper.download_voices --data-dir piper <voice-name>` during setup. The model is loaded once at agent startup via `PiperVoice.load()` and stays resident in-process — no subprocess, no separate server.
- **OpenWakeWord** — Wake word detection from `wakeword.onnx`

## Piper TTS

`PiperVoice.load()` is called once in `BotGUI.__init__` and the voice instance is reused for every utterance. TTS is a two-stage pipeline, so the next sentence is synthesized while the current one plays (Piper takes 0.3–1.4 s per sentence on a Pi 5; synthesizing only after the previous sentence finished left a ~1 s gap after a short opener):

- **Synth thread** (`_tts_worker`, "tts-synth"): takes text from `tts_queue`, applies `normalize_for_tts`, logs `[PIPER SPEAKING]`, and runs `self.piper_voice.synthesize(text)` (`_synthesize`). Each chunk is resampled with `scipy.signal.resample` if the device doesn't take the voice's rate (`_playback_format`, decided once per sample rate) and put on `audio_queue` as `(int16 bytes, rate)`, followed by a `TTS_ITEM_END` marker. `tts_queue.task_done()` comes only after all of the item's audio is enqueued. `tts_active` is set while it works on an item; items are skipped (task_done, no synthesis) while `interrupted` is set.
- **`audio_queue`**: `queue.Queue(maxsize=16)`, so synthesis can't run far ahead; `_put_audio` blocks while it is full and gives up only on exit.
- **Playback thread** (`_playback_worker`, "tts-playback"): owns the only TTS `sd.RawOutputStream`. It opens it on the first chunk of a reply (clearing `playback_idle`), keeps it open across sentences, and writes in 2048-frame (`TTS_WRITE_FRAMES`) sub-chunks, checking `interrupted` between writes. When `audio_queue` is empty, no item is half-played, and the synth thread is idle with nothing queued, it drains and closes the stream and sets `playback_idle`. A pause in Claude's stream longer than that closes the stream; the next sentence reopens it.
- **Draining**: `stream.stop()` does not wait for buffered audio on the Pi's ALSA `default` device (PulseAudio plugin): it returns at once and would cut the last ~0.25 s. `_close_stream` first writes silence (the stream's buffer or reported latency, whichever is larger, plus 0.15 s), so the real audio has been heard when `stop()` drops what is left. This replaces the old fixed 0.5 s sleep after each sentence.
- **Interrupt**: `handle_speaking_interrupt` (Tk thread) sets `interrupted`, clears the thinking sound and drains `tts_queue`; it never touches the stream. The playback thread notices within one write (≤ ~93 ms at 22050 Hz, ~120 ms measured), `abort()`s and closes its stream on its own thread, empties `audio_queue` (task_done each), sets `playback_idle`, and discards any late chunks while `interrupted` stays set. A sentence already being synthesized finishes synthesizing first (Piper can't be stopped mid-sentence), so `wait_for_tts` after an interrupt can take up to about a second.
- **`wait_for_tts()`** means everything queued has been spoken: `tts_queue.join()`, then `audio_queue.join()` (playback task_done's a chunk after writing it), then `playback_idle.wait()` (10 s safety timeout, logged). Every path that ends a turn calls it before the mic can reopen: the end of `chat_and_respond`, its error handler, the memory wipe, and the main loop's per-turn error handler.
- **Exit**: both threads stop when `exiting` is set; the playback thread aborts and closes its stream, and `safe_exit` joins it for up to 0.5 s.

## Configuration

`.env` contains sensitive configuration (API keys). Copy `example.env` to `.env` and fill in your `ANTHROPIC_API_KEY`. It is loaded from `BASE_DIR`, is gitignored, and is kept at mode 0600 by the agent and by `setup.sh`.

`config.json` controls: Claude model name, voice model path, the STT engine (`stt_engine`: "parakeet" or "whisper") and Parakeet threads (`stt_threads`, 1–4), whisper model path, whisper thread count, VAD endpointing (`vad_min_silence`, 0.2–3.0 s, default 0.9; `vad_resume_window`, 0.0–2.0 s, default 0.6; `vad_threshold`, 0.1–0.9, default 0.5), audio energy threshold, chat memory toggle (`chat_memory`, memory.json only), transcript logging toggle (`log_transcripts`, agent.log only), camera rotation, a system prompt extension, microphone selection (`input_device` — index, name substring, or `null` for default), a preferred input sample rate (`input_sample_rate`), how many recent chat messages are resent to Claude each turn (`max_history_messages`, default 20), the RMS-fallback `silence_threshold`, `wake_word_threshold` / `wake_word_consecutive`, `camera_trigger_words` (`[]` = camera never offered), `temperature` (0.0–1.0 or null; default null) and `effort` ("low"/"medium"/"high" or null; default "low"). The script merges user config over `DEFAULT_CONFIG` defaults after `validate_config()`: unknown keys are warned about and dropped; each value is type-checked against its default's type (or `NULLABLE_CONFIG_TYPES`) and range-checked (`CONFIG_RANGES`), and an invalid value is warned about and replaced by the default. All of these print `[CONFIG]` warnings. If `config.json` is not valid JSON (or not an object), the whole file is ignored with a loud error banner.

## Logging

All output goes through the `logging` module: logger `"bmo"` at INFO, root at WARNING (so library warnings are kept but httpx/anthropic INFO chatter is not). Handlers: stdout and `agent.log` in `BASE_DIR` via a `RotatingFileHandler` subclass (1 MB, `LOG_BACKUP_COUNT` = 3 backups, always mode 0600 because it holds transcripts). Lines carrying the user's or the bot's words (`Heard:`, `[PIPER SPEAKING]`, the web search query) go through `log_transcript()`: at INFO with the text when `log_transcripts` is true, otherwise still at INFO but logged as `<redacted, N chars>` (activity without content). `chat_memory` does not affect `agent.log`, and the memory wipe does not purge it. Use `log.info/warning/error/exception`, not `print`. When something fails (API errors, STT, camera, a crashed main loop), the details and tracebacks are in `agent.log`.

`uvx ruff check agent.py` (config in `pyproject.toml`). There are still no tests.

## Display

**A desktop environment (X11/Wayland) is required.** The agent uses tkinter for its GUI, which needs a running display server. A headless/server-only Pi OS installation will fail with `couldn't connect to display ":0"`. If using Pi OS Lite, install `lightdm` and configure desktop autologin via `raspi-config`.

The target display is the Raspberry Pi's DSI touchscreen interface (800x480). The script sets `os.environ.setdefault("DISPLAY", ":0")` at the top of `agent.py` before any tkinter imports, ensuring the GUI renders to the DSI screen regardless of launch context (local terminal, SSH, or systemd service). Users can override by setting `DISPLAY` before running.

`setup.sh` installs a desktop autostart entry: it substitutes the repo path into `be-more-agent.desktop` and copies it to `~/.config/autostart/`, which launches `start_agent.sh` (execs `agent.py` via `.venv`) when the desktop session starts. Remove that file to disable autostart.

## Audio Handling

The agent auto-detects microphone/speaker sample rates and resamples on the fly (using scipy) to match hardware capabilities. This is critical for Pi hardware compatibility — Piper voices typically emit at 22050 Hz (read per-chunk from `chunk.sample_rate`) but many Pi audio devices only support 48000 Hz.

An audio energy gate (`_check_audio_energy`) checks RMS energy of the recorded 16 kHz array before either STT engine runs. If the audio is below the configurable threshold (`audio_energy_threshold` in `config.json`, default `0.002`), transcription is skipped entirely, avoiding unnecessary CPU spikes on blank/silent recordings.
